# Data Sourcing Dossier

## A. Scope
Какие фичи/эпики проанализированы и почему именно они (какие данные им нужны, которых у продукта ещё нет). 3–5 строк.

## B. Источники данных
*(Для каждой фичи, требующей внешних/пользовательских данных, — отдельная секция. Заголовок ОБЯЗАН содержать точную пару `domain/feature_id` из вывода `query-discovery features` — не придуманное название: это единственный ключ, по которому tech-synthesizer перенесёт запись в tech_constraints.yaml, и по которому линтер сверит, что фича реально существует.)*

### [domain/feature_id] — [Человекочитаемое название]
1. **Data Need:** Какие конкретно данные нужны и для какого сценария (Job Story ID).
2. **Candidates (Source Ladder):** 2–3 варианта источника (открытый датасет / API / партнёрский фид / UGC), с лицензией, лимитами, актуальностью.
3. **Automation Verdict:** `automated` / `semi-automated` / `manual-required` — с обоснованием.
4. **Cold-Start Strategy:** Заполняется только если основной источник — сами пользователи (UGC/поведенческие данные). Иначе пропусти секцию.
5. **Moderation & Quality Signal:** Ожидаемый объём новых записей, тип требуемой проверки, автоматизируема ли полностью. Если проверка не нужна — явно укажи "не требуется".
6. **Legal Flags:** Явные риски (лицензия, ToS, PII) — без вердикта, только флаг для compliance-scout. Если рисков не найдено — укажи "не выявлено".
