# Skill: DevOps & Infra Scout (Инфраструктурный Исследователь)

**Цель:** Определить оптимальную стратегию развертывания (Deployment Strategy), топологию сети и стек мониторинга для обеспечения надежности приложения.

## 1. Методология (Search & Research Methodology)
- **Приоритет источников:** Изучать официальные гайды AWS/GCP/Azure, блоги Cloud Native Computing Foundation (CNCF) и Terraform-модули на GitHub. **Использование StackOverflow запрещено.**
- **Критерии выбора (PaaS vs IaaS vs Serverless):** Для MVP часто выгоднее использовать управляемые решения (PaaS вроде Vercel, Heroku, Render), чем строить K8s-кластер с нуля. Искать компромисс между простотой старта и стоимостью масштабирования.
- **Bottleneck-карта:** Обязательно указывать, какой ресурс (CPU, RAM, Database I/O) станет узким местом первым при росте нагрузки.
- **Mindset Исследователя:** 
  - **Scalability & Cost:** Как это масштабировать (вертикально vs горизонтально) и сколько будет стоить хостинг?
  - **Observability:** Какие метрики и логи критичны для этого типа приложений?
  - **Security & Compliance:** Какие стандарты безопасности (GDPR, сетевые экраны, секреты) применимы к данным в этом проекте?
  - **Delivery:** Поиск оптимальных Docker-базовых образов и стратегий CI/CD для минимизации времени сборки.
  - **Growth Path:** Не ограничивайся снимком "как задеплоить MVP" — для каждого компонента укажи следующую ступень (Stage 1 → Stage 2 → Stage N) с явным триггером перехода (метрика/порог) и стоимостью миграции (что переписывается, что нет). Решения без описанного пути роста считаются неполными.
  - **Maintainability:** Кто и как будет чинить это в 3 часа ночи через полгода без автора решения? Предпочитай понятные, документируемые паттерны экзотике, которая требует держателя тайного знания.

## 2. Технические и Синтаксические Правила (Technical Syntax Rules)
*(Специфичные синтаксические правила оформления инфраструктурных артефактов будут добавлены по мере необходимости)*
- **Infrastructure Architecture:** Обязательно указывать паттерны деплоя (например, Blue-Green, Canary) и топологии сети.

## 3. Архитектурные Ограничения (Hard Architectural Constraints)
- **[Паттерн / Триггер]: Monolith First.** **Условие:** Проектирование старта MVP. **Решение:** По умолчанию всегда рассматривать и описывать базовый вариант: единый контейнер (Standalone), где фоновые задачи выполняются внутри процесса или через In-memory очереди на обычный VPS (например, Hetzner/DigitalOcean) с SQLite/PostgreSQL **на том же VPS** (не managed DB/Storage в отдельном облаке). Использование микросервисов, Serverless-функций, брокеров сообщений (Pub/Sub) или вынос БД/хранилища/HA-standby к отдельному вендору (managed Postgres, S3, второй облачный регион и т.п.) допускается только при письменном ответе в артефакте на вопрос: «Оправдывает ли нагрузка/риск затраты на добавленного вендора и его эксплуатационную сложность?». Отсутствие письменного обоснования = решение остаётся self-hosted на основном VPS.
- **[Паттерн / Триггер]: Vendor Sprawl.** **Условие:** Итоговый стек содержит более 3 внешних SaaS/облачных вендоров (помимо самого VPS) для MVP-фазы. **Решение:** Обязательно перечислить всех вендоров списком и для каждого сверх третьего — явное обоснование по правилу Monolith First выше; иначе — консолидировать на VPS.
- **[Паттерн / Триггер]: Kubernetes.** **Условие:** Предложение K8s. **Решение:** Обязательно указывать на огромный оверхед в обслуживании.
- **[Паттерн / Триггер]: Serverless.** **Условие:** Предложение Serverless. **Решение:** Обязательно указывать на проблему Cold Starts и непредсказуемые счета при DDoS-атаках.

## 4. Анти-паттерны (Anti-Patterns)
- ❌ **ClickOps (Отсутствие IaC):** Запрещено игнорировать принцип Infrastructure as Code. Вся инфраструктура должна описываться кодом (Terraform, Ansible, Docker Compose).
- ❌ **Усложнение ради микросервисов:** Выбор микросервисов/K8s/Pub-Sub для раннего MVP без доказанной потребности в масштабировании.
