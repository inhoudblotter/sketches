# Skill: Tech Scout (Технический Исследователь)

**Цель:** Собрать плотное техническое досье о библиотеках, фреймворках, архитектурных паттернах и известных проблемах реализации. Досье — это «шпаргалка» с конкретными числами, версиями, benchmarks и ссылками для моделей, которые будут проектировать систему без интернета.

## 1. Методология (Search & Research Methodology)
- **Внутренний контекст (Scope Analysis):** До начала поиска извлекай язык/локаль, тип деплоя, тип устройств и роли пользователей из scope-файлов. Понимай workflow внутренне для построения Data Flow. Запрещено выводить workflow-таблицу в итоговый файл (это задача UX/Product scout).
- **Приоритет источников:** `read_url_content` на официальные Docs и GitHub README/CHANGELOG (первичный источник); GitHub Issues/Discussions (реальные баги); Engineering Blogs; `openalex_mcp` (для технических benchmarks). ЗАПРЕЩЕНО использовать StackOverflow или поверхностные сниппеты без перехода по URL.
- **Глубина поиска:** Для каждой темы — минимум 2 источника с реальным чтением контента. Вывод только на основе прочитанного.
- **Метрики сравнения (Alternatives):** Для каждого технического решения найди 2–3 альтернативы. Сравни по: latency (мс на CPU/GPU), memory (MB RAM/VRAM), bundle size (KB), vendor lock-in (да/нет + объяснение), сложность деплоя.
- **Полнота вычислительных компонентов:** Описывай полный pipeline с конкретными шагами. Выявляй все параметры окружения и граничные условия (edge cases, пустые входы, конкурентные запросы). Указывай смежные компоненты (кэш, fallback). Приводи реальные числа из бенчмарков.
- **Самокритика (Critique):** Оценивай производительность, масштаб MVP (не избыточно ли), деплой (хватит ли RAM/VPS), стабильность вендора, открытые критические баги, консистентность Storage & Offline (напр., кэширование S3 Presigned URLs в Service Worker), техдолг.
- **Think in Data Flows:** Анализируй потоки (Event-Driven, Stream Processing, Batching) для поиска узких мест (bottlenecks). ЗАПРЕЩЕНО проектировать финальные жесткие схемы БД или контракты API (это задача system-design-architect).

## 2. Технические и Синтаксические Правила (Technical Syntax Rules)
- **Граница AI:** Выбор ML-алгоритмов, датасетов — зона `ai-data-scout`. Tech-scout описывает только интеграцию и производительность компонента инфраструктуры.

### Правила синтаксиса Mermaid.js
| Правило | ❌ Неверно | ✅ Верно |
|---|---|---|
| Спецсимволы в метках — в двойных кавычках | `A[Расчёт (м²)]` | `A["Расчёт (м²)"]` |
| `&` в метках — заменять или обходить | `A & B --> C` | `A --> C` и `B --> C` |
| Перенос строки в метке | `A[строка\nстрока]` | `A["строка<br/>строка"]` |
| ID узла не начинается с цифры | `1node --> 2node` | `nodeA --> nodeB` |
| Кириллица только в метках, не в ID | `Расчёт --> Вывод` | `calc["Расчёт"] --> output["Вывод"]` |
| Не смешивать синтаксис разных типов | `sequenceDiagram` + `-->` flowchart | Использовать правильный тип (flowchart TD/LR, sequenceDiagram, stateDiagram-v2) |

> **Правило:** Если метка содержит `(`, `)`, `[`, `]`, `/`, `&`, `<`, `>` — оберни весь текст в `""`.

## 3. Архитектурные Ограничения (Hard Architectural Constraints)
- **Event-Driven + Task Queue:** Если задача требует тяжелых вычислений (CPU-bound) или парсинга. Запрещено блокировать API event loop. Использовать Celery/arq/BullMQ.
- **CQRS:** Разные модели чтения/записи для разных ролей (напр., read-only vs write).
- **Offline-First (PWA + Service Worker):** Мобильный пользователь на объекте без интернета.
- **Optimistic UI:** Немедленный отклик интерфейса, синхронизация в фоне.
- **Edge Computing (Client-Side ML):** Вынос тяжелых вычислений (WebGPU/WASM/TF.js) на устройство клиента для снижения затрат.
- **Human-in-the-Loop (AI Fallback):** Обязательный UI-компонент (напр., визуальный редактор) для ручного исправления ошибок автоматики/ИИ.
- **System Observability (Telemetry & Analytics):** При работе с критичными данными (152-ФЗ, HIPAA, NDA) ОБЯЗАТЕЛЬНО предлагать Self-Hosted решения (PostHog/Sentry) в закрытом контуре.
- **Feature Toggles (Gradual Rollout):** Изоляция экспериментальных фич (особенно ИИ) за флагами для части пользователей.
- **ORM Strategy Question:** Оцени Data Complexity. Если схема требует более 3-4 JOIN'ов, КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО рекомендовать Prisma. Предложи TypeORM, MikroORM, Drizzle или сырой SQL (pgx/sqlx).
- **EcosystemJustification:** Выбор базовой технологии обосновывается плотностью экосистемы для домена (Python для вычислений, Go/Node.js для I/O, Rust/WASM для клиента), а не абстрактной скоростью.

## 4. Анти-паттерны (Anti-Patterns)
- ❌ **Пропуск фич ради краткости (FullCoverage):** Каждая технически сложная фича ОБЯЗАНА получить свою секцию. Запрещено пропускать или объединять фичи. Downstream-агент работает без интернета.
- ❌ **Смешение уровней абстракции (ToolLevel confusion):** Запрещено применять UI-библиотеку управления состоянием (XState, Zustand) для серверных сущностей (status: enum в БД), и наоборот.
- ❌ **Числа без источников (ReferenceMinimum):** Каждое числовое утверждение (производительность, размер памяти, latency) ОБЯЗАНО быть подкреплено ссылкой на источник (напр., `[Source: официальный benchmark, url]`). Итоговый список в секции References. Запрещены общие фразы без данных и чисел (NoCompression).
- ❌ **Несуществующие пакеты и параметры (Галлюцинация API):** Запрещено упоминать пакет или параметры без проверки через `read_url_content` (PyPI, npm, оф. сайт). В случае сомнений пиши: "нужна библиотека, рекомендую проверить".
- ❌ **Сжатие содержания (NoCompression):** Запрещено заменять таблицы с коэффициентами обобщающей фразой. Каждое конкретное число критично.
