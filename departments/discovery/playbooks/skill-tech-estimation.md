# Skill: Agent-Driven Tech Estimation

**Цель:** Стандартизация оценки технической сложности (Job Stories) для сабагента Tech Estimator. Генерация метрик сложности (Story Points) с учетом рисков галлюцинаций LLM и "Время до доверия" (Time to Trust).

## 1. Концептуальные ограничения (Workflow Constraints)

- **ИИ-центричность оценки (Agent-Centric):** 1 Story Point измеряет риск галлюцинаций LLM и "Время до доверия", а не человеко-дни. Оценка производится строго для ИИ-агента.
- **Разделение сложности и неопределенности:** Сложность задачи не равна степени её неизвестности. Запрещается завышать оценку "на всякий случай" из-за недостатка документации.

- **Story Points как язык для людей, не как токены/деньги:** SP намеренно выбраны размытой относительной шкалой (в духе Cohn), чтобы на этапе discovery снизить неопределённость и говорить об объёме работ на человеко-понятном языке — а не потому что кто-то умеет точно считать токены или стоимость реализации заранее. Реальный расход ресурсов появится позже, на этапах архитектуры/девопса/разработки в других отделах. Поэтому таблица токенов в Шаге 2а — это неоткалиброванная внутренняя прикидка для самопроверки агента, а НЕ источник числовых токен/$-оценок для инвесторов. Инвесторский сигнал объёма — качественный `size_bucket` (см. Шаг 2б), а не арифметика над токенами.

## 2. Операционный Пайплайн (Workflow Pipeline)

### Шаг 1: Анализ осей ИИ-оценки (The ADD Pillars)

- **Триггер:** Поступление Job Story на оценку.
- **Действие:** Оценить задачу по трем параметрам:
  1. _Promptability (Размер контекста):_ Поместится ли в один промпт (CRUD) или требует множества файлов (рефакторинг).
  2. _Verifiability (Проверяемость):_ Способность ИИ написать 100% юнит-тесты (TDD) без визуальной (человеческой) оценки.
  3. _Training Data Blindspot (Окно знаний):_ Опора на публичные технологии vs закрытые/недокументированные API.
- **Обязательный вывод:** Определение уровня риска галлюцинаций для каждого параметра.

### Шаг 2: Маппинг на числа Фибоначчи (Fibonacci Mapping)

- **Триггер:** Риски по осям ADD определены.
- **Действие:** Выбрать СТРОГО одно из чисел Фибоначчи (`1, 2, 3, 5, 8`):
  - **1 SP (Auto-Pilot):** Шаблонный CRUD, бойлерплейт, верстка по дизайн-системе (100% проверяемость).
  - **2 SP (Guided):** Понятная бизнес-логика (1-2 итерации, легко покрывается TDD).
  - **3 SP (Context Heavy):** Кросс-файловый рефакторинг, сложные стейт-машины (требует удержания многих файлов в контексте).
  - **5 SP (Low Verifiability):** Сложные UI/UX паттерны, потоковые данные (ИИ не может протестировать сам).
  - **8 SP (Hallucination Zone):** Работа с недокументированным API, специфичным железом (высокие риски галлюцинаций).
- **Обязательный вывод:** Итоговая базовая оценка (Story Points) и структурированный блок `rationale` (где кратко расписаны `technical_scope`, `promptability`, `verifiability` и `blindspots`). Запрещено использовать комментарии YAML или писать эссе в произвольных полях.

### Шаг 2а: Калибровка через токены (Token Calibration — внутренняя эвристика)

- **Триггер:** Базовая оценка Story Points (Шаг 2) выставлена.
- **Действие:** Сверить свою оценку с ориентировочным разбегом токенов на реализацию (с учётом доработок, правок и ресерча). Это грубая, ничем не откалиброванная прикидка для внутренней самопроверки ("не занижена/не завышена ли оценка"), а НЕ измеренная величина — таблица не проверялась на реальных прогонах. Число токенов никуда не пишется и никуда не экспортируется — в артефакт идёт только `story_points`.

  | SP  | Ориентировочный разбег токенов (с ревизиями) |
  | --- | --------------------------------------------- |
  | 1   | ~1k–4k                                       |
  | 2   | ~4k–8k                                       |
  | 3   | ~8k–20k                                      |
  | 5   | ~20k–40k                                     |
  | 8   | ~40k–80k+                                    |
  | 13+ | Существенно выше 8 SP (кандидат на REJECT, см. Шаг 3) |

  - **Многопрогонные флоу:** таблица откалибрована на объём одного агентного прогона (одна история = одна реализация за раз). Если история фактически покрывает флоу с несколькими экранами/виджетами (много `states` в `user_flows_template.yaml`), которые реалистично будут выполняться отдельными прогонами/агентами, верхняя граница 8 SP — не жёсткий потолок токенов, а ориентир на прогон. Итоговое число Фибоначчи в этом случае агент выбирает сам, исходя из совокупной сложности и числа прогонов, а не подгоняет её под верхнюю строку таблицы.

### Шаг 2б: Инвесторский rollup — Size Bucket, не токены

- **Триггер:** Сумма `story_points` по эпику/домену посчитана (делается downstream-инструментами отчётности, не самим агентом).
- **Действие:** Сумма `story_points` переводится в качественный `size_bucket` по фиксированным порогам — это единственный "объёмный" сигнал, который честно можно дать инвестору на этапе discovery:

  | Сумма SP | size_bucket |
  | -------- | ------------ |
  | 1–3      | `XS`         |
  | 4–8      | `S`          |
  | 9–20     | `M`          |
  | 21–40    | `L`          |
  | 41–80    | `XL`         |
  | 81+      | `XXL`        |

  - Никакой арифметики над токенами/долларами здесь нет и не должно быть — реальный расход ресурсов появится только на этапах архитектуры/девопса/разработки в других отделах. `size_bucket` — это `story_points`, переведённые в ещё один слой человеческого языка, а не псевдо-точный бюджет.

### Шаг 3: Обработка высокой сложности и неизвестности (Spec & Spike Handling)

- **Триггер:** Оценка достигла 13+ SP или задача опирается на непроверенные 3rd party API / недокументированный легаси-код.
- **Действие:**
  - Если задача слишком размыта и уходит в 13+ SP: Отклонить (REJECT), так как агент уйдет в бесконечный цикл ошибок. Требуется декомпозиция.
  - Если задача в зоне галлюцинаций, но видимая сложность <= 8 SP: Зафиксировать оценку (не выше 8 SP) и обязательно добавить тег `[SPIKE REQUIRED]`.
- **Обязательный вывод:** Установка статуса REJECT или добавление тега `[SPIKE REQUIRED]` в `description`, `title` или `flag_justifications` (ключи).

### Шаг 4: Каталог флагов риска (Risk Flag Catalog)

Флаги — не дубли друг друга, а разные оси риска. Каждый пишется в `flag_justifications` только если применим; ставить сразу все "на всякий случай" запрещено (см. Анти-паттерны).

- **`[SPIKE REQUIRED]`** — риск галлюцинаций у исполнителя (Training Data Blindspot, Шаг 1.3). Оценка сделана и ей можно пользоваться, но задача опирается на недокументированный API/легаси — реализация может пойти не с первой попытки.
  - *Триггер:* задача в "зоне галлюцинаций", но видимая сложность укладывается в 8 SP.

- **`[NEED RESEARCH]`** — самой оценке нельзя доверять без внешнего ресёрча (например, через tech-scout), в отличие от SPIKE, где оценка уже надёжна.
  - *Триггер:* `tech_constraints.yaml` не покрывает нужный стек, флоу отсутствует/противоречив, либо SP не стабилизируется (мечется между далёкими числами Фибоначчи) даже после Шагов 1–2а.
  - *Действие:* не гадать и не завышать SP "с запасом" — зафиксировать лучшую оценку и поставить флаг.

- **`[LOW VERIFIABILITY]`** — ИИ не может сам подтвердить качество результата (Verifiability, Шаг 1.2): нет способа покрыть 100% TDD, нужна визуальная/человеческая приёмка.
  - *Триггер:* задача попадает в категорию "5 SP" по Шагу 2 (сложные UI/UX-паттерны, потоковые данные) — риск в том, что скрытые баги вскроются только вручную, а не в CI.

- **`[MULTI-RUN FLOW]`** — история фактически покрывает флоу с несколькими экранами/виджетами, которые реалистично лягут на несколько отдельных агентных прогонов (см. Шаг 2а, "Многопрогонные флоу").
  - *Триггер:* число `states` в связанных `flows/*.yaml` заметно больше, чем можно закрыть за один прогон при выставленном SP.
  - *Зачем инвестору:* номинальный SP истории может визуально выглядеть скромно, а совокупный объём работы — нет; флаг явно на это указывает, не требуя дробить историю прямо сейчас (дробление на атомарные задачи — зона техлидов после архитектуры).

- **`[VENDOR DEPENDENCY]`** — риск не технический, а деловой/договорной: реализация зависит от стороннего API, вендора или партнёра вне контроля команды (SLA, лицензии, доступность, отказ от сотрудничества).
  - *Триггер:* `stories.yaml`/`flows` явно ссылаются на внешнюю систему (например `external_data_updated`, интеграция с API производителя) как обязательное условие для истории.
  - Может сочетаться с `[SPIKE REQUIRED]` (если API ещё и недокументирован), но ставится независимо — это разные риски даже при документированном API.

- **`[SLA CRITICAL]`** — риск инфраструктуры/производительности: связанный `flow` требует жёсткого SLA (`sla.latency_ms`, `sla.throughput`, `sla.availability_target`), выполнение которого требует архитектурных вложений (очереди, кэши, масштабирование), а не просто "написать код".
  - *Триггер:* SLA в `flows/*.yaml` заметно строже нормы для класса задачи (например latency в единицы секунд для события с широким fan-out, availability 99.9%+, agressive retry/throughput).
  - Отличие от `[SPIKE REQUIRED]`: это не про незнакомый API, а про то, что даже знакомый стек может не выдержать заявленные цифры без отдельной инженерной работы.

- **`[SECURITY CRITICAL]`** — риск в духе `[LOW VERIFIABILITY]`, но специфично про безопасность/криптографию: тесты могут проходить, а результат при этом быть небезопасным (утечка данных, некорректная крипто-схема, нарушение изоляции доступа).
  - *Триггер:* `flow` включает крипто-примитивы или чувствительные к безопасности состояния (например `zkp_generation`, `trust_threshold_failed` из `user_flows_template.yaml`, либо явная работа с ключами/PII/авторизацией).
  - Цена тихой ошибки здесь выше, чем у обычного `[LOW VERIFIABILITY]`, поэтому вынесено в отдельный флаг.

- **`[DATA SCIENCE REQUIRED]`** — задача не сводится к обычной разработке: нужна ML/DS-компонента (модель, классификатор, рекомендательная логика) и/или сбор и разметка данных для неё. Это отдельная ось риска: сложность и сроки здесь определяются не кодом, а доступностью и качеством данных, которые тех-эстимейтор оценить не может.
  - *Триггер:* `description`/`acceptance_criteria` истории или связанный `flow` подразумевают предсказание, классификацию, детекцию аномалий, персонализацию и т.п. (например состояние `quality_issue_detected` через анализ фото в `event_triggers`), либо явно требуют датасета/разметки, которых в `tech_constraints.yaml` нет.
  - *Зачем инвестору:* объём работ здесь плохо описывается через SP/токены разработки вообще — реальная стоимость может быть в сборе/разметке данных, а не в написании кода; флаг явно выносит это за скобки обычной оценки, вместо того чтобы прятать в завышенном SP (см. Anti-pattern Uncertainty Padding).
  - Обычно сочетается с `[NEED RESEARCH]`, если непонятно, есть ли вообще нужные данные — но ставится независимо от него, так как остаётся актуальным даже когда данные найдены (сама ML-часть — отдельный риск).

## 3. Правила Файловой Системы и Синтаксиса (File System & Syntax Rules)

- **Fibonacci Values:** Поле оценки должно содержать строго значения из ряда: `1, 2, 3, 5, 8, 13, 21`.
- **Extensible Flag Set:** Ключи `flag_justifications` в первую очередь должны опираться на базовый набор рисков: `[SPIKE REQUIRED]`, `[NEED RESEARCH]`, `[LOW VERIFIABILITY]`, `[MULTI-RUN FLOW]`, `[VENDOR DEPENDENCY]`, `[SLA CRITICAL]`, `[SECURITY CRITICAL]`, `[DATA SCIENCE REQUIRED]`. Однако, если выявлен специфический риск, выходящий за рамки базового каталога, агент **имеет право изобрести новый тег** (например, `[COMPLIANCE RISK]`). Любое текстовое обоснование для флага помещается строго как значение в `flag_justifications`.

## 4. Анти-паттерны (Anti-Patterns)

- ❌ **Human-Centric Mapping (Agile Legacy):** Приравнивание 1 SP к 1 дню работы разработчика.
- ❌ **Uncertainty Padding:** Оценка задачи в 13 или 21 SP "на всякий случай" из-за непроверенных API вместо выставления 8 SP и установки тега `[SPIKE REQUIRED]`.
- ❌ **Token Fabrication:** Выдумывание точного числа токенов или конкретной модели-исполнителя как отдельного поля вывода. Таблица в Шаге 2а — внутренний калибровочный ориентир, а не поле для заполнения.
- ❌ **Research Avoidance:** Натягивание правдоподобной, но необоснованной оценки на неясную историю вместо честной установки `[NEED RESEARCH]`.
- ❌ **Flag Spam:** Проставление всех флагов подряд "для перестраховки" вместо честной проверки триггера каждого — обесценивает сигнал для инвестора.
- ❌ **Free-form Essays & Comments:** Использование YAML-комментариев (`#`) или выдумывание полей вроде `justification` для обоснования оценки. Размышления пишутся строго в `rationale`.
