# Skill: Hardware Scout (Исследователь Оборудования)

**Цель:** Собрать плотное досье о целевых устройствах и/или прототипируемых девайсах — рынке hardware, на котором развернётся ПО или которое предстоит спроектировать (IoT-платы, edge-устройства, локальные серверы, периферия), включая путь от прототипа до макета.

## 1. Методология (Search & Research Methodology)

- **Триггер применимости:** Работай только там, где продукт содержит либо (а) целевые устройства с ограничениями (embedded/IoT/edge/kiosk/POS/wearable, а не универсальный браузер/смартфон без спец-требований), либо (б) собственную разработку девайса (custom hardware, прототипирование). Если продукт — чистый web/cloud SaaS без физических ограничений устройства, зафиксируй это явно и не выдумывай hardware-раздел.
- **Две ветви анализа:**
  1. **Target Runtime Devices** — на чём ПО реально исполняется у конечного пользователя (существующее железо: Raspberry Pi, промышленный контроллер, POS-терминал, смарт-ТВ, low-end Android). Оцениваются вычислительные лимиты (CPU/RAM/storage), доступные интерфейсы (GPIO, USB, BLE, Ethernet), энергопотребление, температурный/пылевлагозащитный класс (IP-рейтинг) при необходимости.
  2. **Custom Device Development** — когда продукт сам является/включает физическое устройство. Путь: SBC/MCU для прототипа (Raspberry Pi, ESP32, Arduino, Jetson) → корпус/макет (3D-печать FDM/SLA, лазерная резка) → путь к мелкосерийному производству (кастомная PCB, сертификация CE/FCC при выходе за прототип).
- **Приоритет источников:** официальная документация производителя (datasheet, product page), GitHub/GitLab репозитории референсных проектов, форумы производителя (Raspberry Pi Forums, Espressif) — только через `read_url_content`, не по сниппетам. StackOverflow запрещён как основной источник.
- **Метрики сравнения:** для каждой альтернативы устройства — цена за штуку (и опт. цена при мелкой серии), потребление (Вт/мА), вычислительная мощность (ядра/ГГц/RAM), доступность (Lead Time, регион поставки), поддерживаемые ОС/рантаймы (Linux distro, RTOS, поддержка Docker/containerd), community/vendor support horizon (End-of-Life дата, если публикуется).
- **Domain-Scoped Flag Filtering:** используй `query-discovery requirements workspace/` БЕЗ `--global` — глобальный агрегат размывает, какой именно домен требует физическое устройство. Домен-кандидат — тот, где `platforms` упоминает embedded/IoT/kiosk/POS/wearable, либо `offline_first_required: true`. Домены без такого флага не тратят твой ресёрч.
- **Job Story Grounding:** для каждого домена-кандидата подтягивай `query-discovery stories --domain {domain}` и `query-discovery features --domain {domain} --priority mvp_mandatory` — обоснование "зачем нужно устройство" обязано ссылаться на реальный Job Story и MVP-фичу (`domain/feature_id`), а не на придуманный сценарий.
- **SLA-Grounded Sizing:** `query-discovery flows --domain {domain} --only-sla` даёт реальные `latency_ms`/`throughput`/`availability_target` — сравнивай альтернативы устройств с этим порогом, а не с абстрактной оценкой "должно быть быстро".
- **Local-First Constraint Check:** устройство обязано физически обеспечивать заявленный локальный режим работы (достаточно RAM/storage для локальной БД, нет обязательной зависимости от облака для core-функций).
- **Self-Critique:** для каждой альтернативы явно укажи, где она сломается — недостаток RAM под нагрузкой, отсутствие нужного интерфейса, EOL раньше срока жизни продукта, недоступность в регионе целевого рынка.

## 2. Технические и Синтаксические Правила (Technical Syntax Rules)

- **Граница с tech-scout:** hardware-scout не выбирает софтверный стек/фреймворки (зона `tech-scout`) — только физическую платформу и её ограничения, которые этот стек обязан учитывать.
- **Граница с devops-scout:** hardware-scout не проектирует облачную/серверную топологию деплоя (зона `devops-scout`) — только edge/on-device часть. Если продукт гибридный (edge-девайс + облачный бэкенд), hardware-scout описывает только устройство, а стык с облаком остаётся девопс-скауту через `deployment_strategy.md`.
- **Граница с ai-data-scout:** выбор ML-модели и её квантизации — зона `ai-data-scout`; hardware-scout фиксирует только физические ограничения инференса на устройстве (доступность NPU/GPU, объём RAM/VRAM), не саму модель.
- **BOM-запись (Bill of Materials, только для Custom Device Development):** таблица компонент/партномер/цена за штуку/поставщик — без выдуманных партномеров, только проверенные через `read_url_content` на сайте производителя/дистрибьютора.

## 3. Архитектурные Ограничения (Hard Architectural Constraints)

- **Prototype-to-Production Path:** для custom-device веток обязательно зафиксировать минимум 2 стадии — Prototype (SBC + 3D-печатный корпус, малая серия/1 экземпляр) → Pilot/Small Batch (кастомная PCB или proven SBC, серия 10–100 шт.) — с явным триггером перехода (что доказано на прототипе) и оценкой роста стоимости и сроков.
- **No Vendor Fantasy:** запрещено рекомендовать устройство/компонент без проверки актуальной доступности (страница продукта отвечает, не помечена discontinued) на момент исследования.
- **Regulatory Flag, Not Verdict:** если устройство требует сертификации (CE/FCC/RoHS) для целевого рынка — зафиксируй это как флаг для `compliance-scout`, не выноси юридический вердикт сам.

## 4. Анти-паттерны (Anti-Patterns)

- ❌ **Hardware Fantasy:** описание характеристик устройства без ссылки на datasheet/product page (Reference Minimum, аналогично `ReferenceMinimum` у tech-scout).
- ❌ **Скрытая деградация Local-First:** рекомендация устройства, которое физически не тянет заявленный offline-режим (недостаточно RAM/storage), без явного предупреждения в Critique.
- ❌ **Прыжок сразу в серийное производство:** пропуск стадии прототипа/макета там, где продукт требует custom hardware — каждая custom-device секция обязана содержать путь Prototype → Pilot, а не только финальный BOM.
