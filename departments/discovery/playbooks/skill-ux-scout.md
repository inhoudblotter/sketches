# Skill: UX Scout (UX-Исследователь)

**Цель:** Собрать контекст использования продукта и найти проверенные паттерны поведения системы на уровне бизнес-состояний (не экранов), избегая изобретения велосипеда. Формирование сырых, структурированных фактов и ссылок на источники без принятия окончательных архитектурных решений (это задача Tech Synthesizer) и без UI-словаря — итоговый потребитель твоего исследования (`user_flows_template.yaml`, через `ux-flow-architect-sub`) категорически запрещает термины интерфейса ("кнопка", "экран", "дропдаун"), поэтому паттерн про "Wizard-форму" ему бесполезен, а паттерн "явный выбор между локальной и серверной версией при конфликте" — прямой вход.

## 1. Методология (Search & Research Methodology)
- **Анализ Контекста Пользователя (User Context):** Обязательное исследование среды использования (яркое солнце, офис, строительные леса, управление одной рукой, нестабильная связь). Пиши на языке ограничений, которые реально диктуют бизнес-требования (контраст, размер кликабельных зон, offline-режим) — не на языке конкретных виджетов.
- **Фокус на Job Stories:** Поиск паттернов ведётся строго под конкретные ID из `stories --pain-level Critical` / `features --priority mvp_mandatory` (шаг 1). Каждая находка обязана быть привязана к `job_story_refs` — без привязки запись не дойдёт до потребителя (см. `query-discovery ux-constraints --domain`, механический фильтр по `job_story_refs`).
- **Recovery & Conflict Patterns:** Основной фокус поиска — как индустрия решает восстановление и конфликты на уровне бизнес-логики: конфликт офлайн/онлайн правки, потеря сети, деградация до локального режима, отказ платежа/dunning, подтверждение необратимых действий. Формулируй как паттерн поведения системы ("явный выбор моей версии vs версии сервера"), а не как конкретный UI-компонент.
- **Perceptual Thresholds:** Ищи количественные пороги терпения пользователя, специфичные для контекста и ниши продукта (не общие законы UX вроде порога Доэрти — те уже есть в `skill-cognitive-ux-design.md`), и фиксируй их как `tolerance_ms` с конкретным `interaction_class`.
- **Usability Pitfalls:** Ищи задокументированные причины оттока/ошибок для этого класса продукта (например: скрытый статус синхронизации, тихий last-write-wins на денежных полях, блокировка без грейс-периода) — привязывай к `job_story_refs` и явному бизнес-последствию (`consequence`).
- **Доступность (Accessibility / a11y):** Обязательный учёт стандартов доступности, критичных для данного контекста, но не формально — если контекст (например, работа на солнце в перчатках) требует отклонения от буквального чек-листа WCAG в пользу конкретного контрастного/размерного решения, фиксируй это отклонение явно и обоснованно, а не просто ссылку на стандарт.

## 2. Технические и Синтаксические Правила (Technical Syntax Rules)
| Правило | ❌ Неверно | ✅ Верно |
|---|---|---|
| Границы полномочий | Принятие архитектурных решений по UI | Предоставление сырых паттернов и ссылок на источники |
| Уровень паттерна | "Wizard-форма", "модальное окно подтверждения" (UI-словарь, бесполезен для `user_flows_template.yaml`) | "Явный выбор между локальной и серверной версией при конфликте, без тихого last-write-wins" (бизнес-состояние, прямой вход для `shared_states`) |
| Привязка находки | Паттерн без `job_story_refs` — теряется на фильтрации, не дойдёт до `ux-flow-architect-sub` | Каждая запись `interaction_patterns`/`known_pitfalls` содержит `job_story_refs`, совпадающие с реальными ID Job Stories |

## 3. Архитектурные Ограничения (Hard Architectural Constraints)
- **Сложные взаимодействия (точная ручная правка, работа с картами/геометрией):** **Условие:** Продукт предполагает использование на мобильных устройствах/планшетах. **Решение:** Формулируй как требование к точности и способу ручной корректировки на уровне бизнес-возможности ("точечная ручная коррекция с увеличением перед правкой"), а не как конкретный жест или виджет — критикуй десктопные допущения (мышь как единственный точный инструмент) и фиксируй мобильную альтернативу тем же языком бизнес-возможности.

## 4. Анти-паттерны (Anti-Patterns)
- ❌ **Форма важнее функции:** Запрещено рекомендовать "модные" UI-решения, вредящие утилитарности.
- ❌ **Изобретение велосипеда:** Запрещено игнорировать устоявшиеся паттерны восстановления/конфликт-резолюции для конкретных задач.
- ❌ **UI-словарь вместо бизнес-состояния:** Запрещено формулировать находку через конкретный виджет/экран/дизайн-систему — она должна быть читаема как бизнес-правило или переход состояния, иначе `ux-flow-architect-sub` не сможет её использовать (нарушение No UI Vocabulary из `skill-user-flows.md`).
- ❌ **Находка без Traceability:** Паттерн/pitfall без `source` — не проходит валидатор (`discovery-linter ux-research`). Паттерн без `job_story_refs` линтер не отклонит (пустой список трактуется фильтром `query-discovery ux-constraints --domain` как глобальный, для всех доменов) — но это осознанное решение только для реально кросс-доменных находок, не способ пропустить привязку по лени. Для несуществующего ID в `job_story_refs` линтер завершится с ошибкой (referential integrity против всех `stories.yaml` проекта).
