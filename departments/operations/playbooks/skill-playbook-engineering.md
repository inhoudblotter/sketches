# Skill: Playbook Engineering (Проектирование Плейбуков)

**Цель:** Операционная инструкция по каталогизации, форматированию и созданию плейбуков (`skill-*.md`). Гарантирует предотвращение раздувания контекста (Context Bloat) и стандартизацию механизмов передачи знаний (Knowledge Transfer) в мультиагентных системах.

## 1. Концептуальные ограничения (Workflow Constraints)

- **Минимально Необходимый Контекст:** Принцип "Need to know". Агенту запрещено грузить плейбук, если он может выполнить задачу (заполнить контракты) без него.
- **Отказ от "Эссе и Воды" (Token Waste):** Описание истории концепта или примеров из чужих индустрий запрещено. Плейбук должен давать только вектор применения и жесткие границы.
- **Запрет на Format Bleed:** Категорически запрещено смешивать философские концепции (Type A) с операционными правилами (Type B/C) в одном документе.

## 2. Операционный Пайплайн (Workflow Pipeline)

### Шаг 1: Определение типа знаний

- **Триггер:** Необходимость зафиксировать новые правила или ограничения для агента.
- **Действие:** Выбор подходящего шаблона (Type A, B, C, или D) в зависимости от характера знаний.
- **Обязательный вывод:** Выбор одного из 4 жестких типов. Смешение форматов блокирует создание плейбука.

### Шаг 2: Создание и Инъекция

- **Триггер:** Шаблон выбран.
- **Действие:** Заполнение плейбука в строгом соответствии с контрактом шаблона. Включение пути к созданному плейбуку в секцию `<required_skills>` промпта целевого агента.
- **Обязательный вывод:** Валидный `.md` файл, не превышающий лимиты по весу.

## 3. Правила Файловой Системы и Синтаксиса (File System & Syntax Rules)

- **Директории:**
  - Все шаблоны плейбуков хранятся в `departments/operations/contracts/`.
  - Все сгенерированные плейбуки хранятся в `departments/operations/playbooks/`.
- **Ограничение Веса (Size Limits):** Суммарный вес всех загружаемых плейбуков в секции `<required_skills>` одного агента не должен превышать 100 КБ. Если лимит превышен — необходимо декомпозировать агента или "просушить" текст (Hyper-dense formatting).
- **Синтаксис шаблонов:** Плейбуки должны жестко следовать заголовкам 1-го и 2-го уровня из своих шаблонов.

## 4. Анти-паттерны (Anti-Patterns)

- ❌ **Свалка форматов (Format Bleed):** Смешение философии и операционных инструкций (например, как называть файлы) в одном плейбуке.
- ❌ **Детерминированный If-Else (Creativity Killer):** В философских (Type A) плейбуках нельзя давать жесткие инструкции "Если А, пиши Б".
- ❌ **Раздувание (Context Bloat):** Добавление плейбуков "на всякий случай" агентам, которым они не критичны для работы.

## 5. (Опционально) Каталог Типов Плейбуков (Reference Catalog)

### Type A: Socratic Playbook (Мировоззрение)

- **Суть:** Векторы мышления для стратегов и визионеров.
- **Структура:** Концептуальные Якоря, Сократические Линзы, Анти-паттерны мышления. Шаблон: `playbook_socratic_template.md`.

### Type B: Operational Playbook (Рабочие процессы)

- **Суть:** Инструкция для агентов-исполнителей (синтез, маппинг, QA) о том, как генерировать артефакты.
- **Структура:** Workflow Pipeline, File System Rules, Formatting Constraints. Шаблон: `playbook_operational_template.md`.

### Type C: Technical Standard (Технические Инструкции)

- **Суть:** Ограничения для архитекторов и инженеров (синтаксис, лимиты, бенчмарки).
- **Структура:** Methodology, Syntax Rules, Hard Constraints. Шаблон: `playbook_technical_template.md`.

### Type D: Reference Catalog (Справочный Каталог)

- **Суть:** Структурированная база знаний, паттернов или уязвимостей для случайного доступа (random access). Идеально для сборников анти-паттернов или каталогов архитектурных решений.
- **Структура:** Сводная таблица (Индекс) -> Детальные элементы каталога (Симптом + Решение). Шаблон: `playbook_catalog_template.md`.
