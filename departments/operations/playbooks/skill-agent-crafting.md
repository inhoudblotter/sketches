# Skill: Agent Crafting & Tooling (Проектирование Агентов)

**Цель:** Определение технических стандартов, синтаксических правил (Prompt Engineering) и методологии проектирования доменно-нейтральных агентов, саб-агентов и системных тулзов (Tooling).

## 1. Методология (Agent Design Methodology)

- **Атомарность и Доменная Нейтральность:** Агент не привязан к бизнес-логике, он является абстрактным процессором (Input -> Transformer -> Output). Системные промпты очищаются от индустриальных кейсов (AI Bias). Агент должен быть способен обработать датасет из другой индустрии без изменения промпта.
- **Управление Контекстом (Context Window Engineering):** LLM деградируют при избытке контекста (Attention Dilution). Применяется Business-Sliced Design. Контекст группируется строго по доменам. Передача 1 Эпик = 1 Батч.
- **Инструменты и Делегирование (Agent-in-Agent):** Истинная автономность достигается передачей оркестрации внутрь промпта (например, через `<for_each>`). Агент должен уметь делегировать подзадачи саб-агентам и дожидаться их выполнения, вместо внешнего микроменеджмента скриптами.
- **Температурный режим (Temperature Control):** 
  - `0.0 – 0.2`: Парсинг, извлечение фактов, расчёты. 
  - `0.5 – 0.8`: Синтез, генерация кода, разработка стратегии.

## 2. Технические и Синтаксические Правила (Prompt Syntax Rules)

### Структура Prompt Template
Каждый агент ОБЯЗАН содержать следующие XML-секции в промпте (согласно `agent_template.md`):
- `<role>`: кто агент и что делает (вход/выход).
- `<required_skills>`: пути к playbooks.
- `<mindset>`: 2-3 Socratic-вопроса.
- `<guardrails>`: жёсткие запреты (Traceability, No Role Bleed, Escalation).
- `<output_format>`: блок `<thinking>` + генерация.
- `<workflow>`: пронумерованные шаги с `[SUCCESS]` и `max_steps`. Каждый шаг снабжён `<description>` — единственным местом, где формулируется ЦЕЛЬ чтения/записи для этого шага. Файлы и вызовы объявляются тегами из раздела "Теги Ввода-Вывода и Вызовов" ниже — отдельных блоков `<inputs>`/`<outputs>`/`<contracts>` в промпте нет.
- `<escalation_protocol>`: `<triggers>` (конкретные условия) и `<action>` (ссылка на `escalation_report_template.md`).

### Теги Ввода-Вывода и Вызовов (I/O & Invocation Tags)
Вся работа с файлами и внешними вызовами декларируется точечно, прямо внутри `<workflow>`, пятью тегами (`optional`/`contract`/`condition`/`reason` — компонуемые атрибуты, а не отдельные теги):

| Тег | Назначение | Пример |
|---|---|---|
| `<read>` | Агент обязан прочитать файл перед тем, как продолжить шаг. | `<read>workspace/discovery/strategy/market_context.md</read>` |
| `<read optional="true">` | Файл может отсутствовать — отсутствие не блокер. | `<read optional="true">workspace/discovery/errata/global_errata.yaml</read>` |
| `<write>` | Агент производит файл на этом шаге (текст генерируется самим LLM, а не утилитой). | `<write>workspace/discovery/strategy/market_context.md</write>` |
| `<write contract="...">` | Файл обязан соответствовать шаблону — путь к шаблону указывается прямо здесь, а не в отдельном блоке `<contracts>`. | `<write contract="departments/discovery/contracts/market_context_template.md">workspace/discovery/strategy/market_context.md</write>` |
| `<write optional="true" condition="...">` | Файл создаётся не всегда, а только при выполнении условия — `condition` фиксирует это условие человекочитаемо. Отсутствие файла — легитимный исход, а не баг. | `<write optional="true" condition="найдены actionable blockers после triage">workspace/discovery/errata/critical_errata.yaml</write>` |
| `<call_tool name="...">` | Вызов локального CLI-инструмента (линтер, генератор, препроцессор). `name` обязан совпадать с именем директории тула или полем `name` в его `meta.yaml` — ЛИБО быть одним из системных исключений (см. ниже). | `<call_tool name="validate_pitch_deck">python departments/discovery/tools/validate_pitch_deck/command.py workspace/...</call_tool>` |
| `<call_agent name="...">` | Делегирование саб-агенту. Тело тега — единственное сообщение, которое агент получает, ЗА ИСКЛЮЧЕНИЕМ обязательного технического поля `WORKSPACE_ROOT` (абсолютный путь), которое оркестратор обязан прикладывать к каждому вызову независимо от Brief Delegation — это не бизнес-инструкция, а координата исполнения. | `<call_agent name="product-scout">COMMAND: Conduct Research</call_agent>` |
| `<for_each collection="..." item="..." execution="parallel|sequential" [max_concurrent="N"]>` | Map-Reduce итерация по коллекции (файл-манифест или glob-путь). Внутри — `<read>`/`<write>` с плейсхолдером `{item}`. **Для `execution="parallel"`: атрибут `max_concurrent` обязателен, значение 1–5 (см. PIT-16 в `skill-agentic-pitfalls.md`).** | `<for_each collection="workspace/discovery/domains/*" item="domain" execution="parallel" max_concurrent="5"><read>workspace/discovery/domains/{domain}/dictionary.yaml</read></for_each>` |

**Правила:**
- Один тег `<read>`/`<write>` — один файл. Не перечислять несколько путей внутри одного тега через запятую или список — это ломает парсинг и мешает LLM воспринимать каждый файл как отдельное действие.
- Атрибут `reason="..."` на `<read>`/`<write>` — исключение, а не правило. Используй его, только если в рамках одного шага несколько файлов служат разным, не пересекающимся целям и `<description>` шага не может сформулировать общую цель для всех сразу. По умолчанию цель формулируется один раз в `<description>` — не дублируй её на каждый файл.
- `<read>`/`<write>` — глагольные, императивные теги (аналогично `<call_tool>`/`<call_agent>`), а не декларативный список метаданных. Это намеренно: агент воспринимает их как команду к действию здесь и сейчас, а не как сведения о проекте вообще.
- Любая аналитическая инструкция о том, *как* интерпретировать файл (а не просто зачем его читать), остаётся обычной прозой рядом с тегом. Теги заменяют только механическую формулировку "прочитай/сгенерируй X", а не содержательное рассуждение.
- **`optional` на `<write>` требует `condition`:** В отличие от `<read optional="true">` (файла может не быть — это про чужой артефакт), `<write optional="true">` описывает собственное поведение агента, и без явного условия неотличимо от "агент решил не утруждаться" (PIT-07, Лень и Сокращения). Типовой случай — условные errata/feedback-артефакты (`critical_errata.yaml`, `feedback_{scout_name}.md`): агент пишет их, только если реально нашёл проблему. Всегда сопровождай такой `<write>` атрибутом `condition="..."`, формулирующим триггер в одну фразу. Если файл пишется всегда, но с разным содержимым в зависимости от исхода (например, "No actionable blockers found" вместо списка) — это НЕ `optional`, `write` обязателен, а условность — внутри содержимого файла.
- **Симметрия producer/consumer:** Если производитель помечает файл `<write optional="true">`, любой потребитель этого файла обязан читать его через `<read optional="true">`, а не как обязательный вход. Расхождение (producer optional, consumer required) — латентный баг: потребитель эскалируется на файл, которого по контракту может законно не быть.
- **Канонический паттерн errata-пути:** Точечная (не агрегированная) errata-запись живёт рядом с остальными артефактами той единицы ответственности, которая её породила — тем же местом, где эта единица уже пишет свои другие файлы (в Discovery: `domains/{domain}/domain_errata.yaml` для ошибок уровня домена, `domains/{domain}/epics/{epic_name}/errata.yaml` для ошибок уровня эпика — так же, как `stories.yaml`/`estimation.yaml` уже лежат внутри `epics/{epic_name}/`). Если родительский unit и его дочерний sub-unit оба пишут errata (два разных producer'а), их файлы обязаны иметь РАЗНОЕ имя файла, а не только разную директорию — glob-матчинг в этом проекте построен на `fnmatch`, где `*` пересекает `/` как обычный символ, так что паттерн `domains/*/domain_errata.yaml` технически совпадёт и с более глубоким `domains/*/epics/*/domain_errata.yaml`, если оба файла назвать одинаково `errata.yaml`; разное имя (`domain_errata.yaml` vs. `errata.yaml`) исключает эту коллизию независимо от глубины пути. Без этого граф зависимостей (`pipeline-analysis`) не сможет понять, какой producer какому consumer'у соответствует, и может ошибочно связать разнофазных агентов циклом. Это не относится к агрегированным сводкам уровня отдела (`critical_errata.yaml`) — те собираются поперёк всех unit'ов (например, через `query-discovery errata-global --status all`) и не обязаны следовать этой форме.
- **Прогрессивное чтение (Just-in-Time Attention Focus, см. PIT-01 в `skill-agentic-pitfalls.md`):** Размещай `<read>` в том шаге, где файл непосредственно используется в рассуждении, а не одним блоком "про запас" в начале `<workflow>`. Объединяй несколько `<read>` в одном шаге только тогда, когда анализ реально требует одновременного сопоставления всех файлов сразу (например, синтез конфликтующих отчётов скаутов). Если файлы расходуются последовательно для разных целей — разноси их по разным шагам, чтобы не разбавлять внимание модели контекстом, который ей пока не нужен.
- **Системные исключения в `<call_tool name="...">`:** `name` обязан резолвиться в тул из `departments/*/tools/` — кроме фиксированного списка системных бинарей, которых там нет и не будет: `git`. Используй `<call_tool name="git">` только для операций из Git Sync конвенции (`checkout -B`, `merge --no-ff`, `push`) в `<guardrails>`/`<workflow>` мастер-агентов — не для произвольных shell-команд. Любой `{item}` внутри `<read>`/`<write>` обязан быть объявлен одним из двух способов: (1) атрибутом `item=` ближайшего охватывающего `<for_each>` — агент сам управляет итерацией; (2) полем в `<invocation_contract>` (например, `DOMAIN: {domain}`) — для саб-агентов, которым значение подставляет вызывающий агент, а собственного `<for_each>` в их промпте нет. Использование `{placeholder}`, не объявленного ни одним из этих двух способов, — ошибка контракта.
- **Brief Delegation vs Координаты Исполнения:** `Brief Delegation` ограничивает содержание бизнес-задачи, но не освобождает от передачи технических координат исполнения (рабочая директория).

## 3. Архитектурные Ограничения (Hard Architectural Constraints)

- **Явные Артефактные Контракты (Explicit IPC):** В теле тега `<read>`/`<write>` запрещено указывать голую директорию и запрещён glob (`*`) — путь обязан вести к конкретному файлу, с единственной параметризацией через плейсхолдер итерации `{item}` (привязанный к охватывающему `<for_each>`, см. "Привязка плейсхолдеров" выше). Glob разрешён ровно в одном месте во всей системе — атрибуте `collection=` у `<for_each>`. Если нужно прочитать несколько файлов по маске без действия на каждый в отдельности (просто как совместный контекст) — это всё равно `<for_each collection="..." item="...">` с одним `<read>{item}</read>` внутри; отдельного механизма для этого не существует, чтобы не плодить два разных способа выразить одно и то же. Правило одинаково для любого отдела. `<write>` никогда не принимает `collection=` — запись всегда идёт по одному файлу с уникальным содержимым.
- **Валидация (Linter Validation):** Валидация (через `cli.py`) происходит в конце `<workflow>` перед `[SUCCESS]`. Для `<for_each>` применяются пакетные/макро-линтеры. Категорически запрещено вызывать `<call_tool>`-линтеры внутри `<for_each>`.
- **Business Observability (No Role Bleed):** Бизнес-агенты проектируют только State Machines. Запрещено упоминать технический стек (БД) или UI-решения, если это не их домен.

## 4. Анти-паттерны (Anti-Patterns)

- ❌ **Бесконечные циклы:** Отсутствие `max_steps` в `<workflow>` или попытки эскалации через шаги workflow, а не через `<escalation_protocol>`.
- ❌ **Галлюцинации (Zero-Hallucination Sandbox):** Генерация данных, отсутствующих во входных артефактах (нарушение правила Traceability). Конвейер не прощает подразумевающихся вещей.
- ❌ **Частичная генерация при эскалации:** При срабатывании триггера агент должен записать handoff-файл и немедленно завершить работу. Генерация целевого артефакта запрещена.
- ❌ **Дублирование путей в триггерах:** Указание полных путей в `<triggers>`, если они уже перечислены в шаге `<workflow>`. Оптимизация: `"Любой из входных файлов шага N не найден"`.

## 6. Git Workflow Convention

- **Conventional Commits:** `type(scope): message`, на английском (`feat(discovery): ...`, `fix(operations): ...`).
- **Ветки и Изоляция (Worktree Isolation):** Родительские (оркеструющие) агенты ОБЯЗАНЫ вызывать `<call_tool name="EnterWorktree">{}</call_tool>` первым шагом в `<workflow>` (до `git checkout -B`). Это создает песочницу и позволяет безопасно выполнять параллельных саб-агентов без блокировки файловой системы. `develop` — рабочая интеграционная ветка. `[dept]/[task]` — ветка под конкретную фичу/задачу. Саб-агенты не создают собственных веток — они работают внутри ветки и изолированного ворктри, в которых их вызвал оркестратор. Флаги вроде `isolation="worktree"` при вызове `<call_agent>` запрещены.
- **Merge и Возврат:** интеграция в `develop` строго через `--no-ff` (сохраняет топологию фичи в истории). Force-push запрещён; `--force-with-lease` — единственное допустимое исключение. После мержа и пуша в `develop` (в конце своего workflow), оркестратор ОБЯЗАН выполнить `git checkout [dept]/[task]` для возврата в исходную ветку.
- **Scoped Commit (саб-агенты):** `git add {own_write_paths}` — саб-агент коммитит СТРОГО те пути, которые сам записал на этом запуске (включая обновлённые/новые файлы `patches/`, если это был Patch Run — см. `skill-patch-protocol.md`). `git add -A`/`git add .` и `git push` саб-агенту запрещены категорически.
- **Push в remote:** выполняет только мастер-оркестратор, и только в конце своего собственного workflow — `git push origin develop` (или релевантная feature-ветка), никогда посреди цикла делегирования саб-агентам.

## 7. Multi-Tool & Aggregator Pattern

- **Тип `aggregator` в `meta.yaml`:** тул с несколькими независимыми sub-command, каждый из которых читает/пишет свой собственный срез домена. Эталонный пример — `departments/discovery/tools/analyzers/query_discovery/meta.yaml`.
- **Per-subcommand `inputs`/`outputs`:** у aggregator-тула нет единого top-level `inputs`/`outputs` — у каждого subcommand свой собственный список, потому что разные subcommand читают/пишут непересекающиеся артефакты. Top-level `inputs`/`outputs` допустимы ТОЛЬКО для однокомандных (`type: analyzer`/`linter` с одним входом) тулов.
- **Разрешение subcommand в графе:** `pipeline_analysis` не матчит aggregator-тул по одному имени — он парсит текст самого `<call_tool>` вызова, находит CLI-имя тула, и берёт первый non-flag токен после него как реальный subcommand (см. `_invocation_subcommand` в `graph_builder.py`). Никакого дополнительного дифференцирующего парсинга по флагам агент писать не должен — имя subcommand обязано самодостаточно указывать на конкретный срез данных (см. §8).

## 8. Subcommand Naming Convention

- **Правило:** имя subcommand = `{action}-{scope}`, где `scope` явно называет зону/уровень данных, которые он читает или пишет — а не только глагол действия.
- ✅ `errata-domain` (зона po-strategist, `domain_errata.yaml`), `errata-epic` (зона ux-flow-architect, `epics/*/errata.yaml`), `errata-global` (агрегация, оба уровня — только для aggregation-фазы), `patches-domain` (зона discovery, `patches/*.yaml`), `patch-errata-domain` (кросс-ссылка патч↔errata).
- ❌ `errata` — непрозрачно, не видно чей это срез и на каком уровне.
- ❌ `errata-all` — звучит как "все статусы (open+resolved)", а не "все уровни (domain+epic)"; двусмысленность между scope и status-фильтром.
- **Anti-pattern — виртуальные subcommand через флаги:** разделение доступа по значению флага (например, `errata --status open` vs `errata --status all` как два разных "зоны") запрещено. Флаг — это фильтр внутри одного subcommand, а не способ закодировать разные зоны ответственности; такое разделение невидимо для графа зависимостей (`pipeline_analysis` видит один subcommand `errata` и не может развести два разных потребителя по зонам) и требует хрупкого парсинга сырого текста вызова (`_errata_variant`-паттерн — устранён именно по этой причине).

## 9. (Опционально) Каталог Архитектурных Паттернов (Reference Catalog)

### Socratic Idea Generation & Lenses
- **Симптом/Условие:** Агенту требуются жесткие директивы "делай X, затем Y", либо он выдает слишком предсказуемые, утилитарные решения (вертикальное мышление LLM).
- **Решение/Внедрение:** Заменить директивы в `<mindset>` на эвристические вопросы (например, "Где в этой архитектуре возникает SPOF?"). Для нестандартных задач использовать "Сократовские Линзы" — парадоксальные установки, ломающие привычный паттерн (например, "Линза инверсии: спроектируй систему так, словно сеть всегда нестабильна").

### Structured Output as Chain of Thought (Форсированное Рассуждение)
- **Симптом/Условие:** Агент генерирует поверхностные или галлюциногенные идеи, пропуская этап анализа контекста.
- **Решение/Внедрение:** Использовать YAML/JSON контракты не только для стандартизации, но и как алгоритмический коридор. Обязать агента заполнять ключи строго последовательно (например, `1_abstract_analysis`, `2_constraint_identification`, `3_solution_proposal`), заставляя LLM произвести глубокий синтез до выдачи финального результата.

### File-Based Handoff Protocol
- **Симптом/Условие:** Агент сталкивается с критической ошибкой (файл не найден).
- **Решение/Внедрение:** Заполнить `workspace/[dept]/handoff/[agent_name].md` по шаблону `escalation_report_template.md` и прервать выполнение (Stateless Escalation).
