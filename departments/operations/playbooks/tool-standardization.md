# Skill: Tool Standardization & Architecture (Стандартизация Инструментов)

**Цель:** Обеспечение строгой, предсказуемой и анализируемой архитектуры для всех локальных CLI-инструментов, линтеров и генераторов. Замена спагетти-кода на чистые принципы ООП/ФП с явным декларированием возможностей через метафайлы.

## 1. Метафайлы Инструментов (meta.yaml)

Любой локальный скрипт, вызываемый агентом, обязан иметь файл `meta.yaml` в корне своей директории. Парсеры конвейера используют этот файл для отрисовки пайплайн-графа и аудита автоматизации.

**Формат `meta.yaml`:**

```yaml
name: [Удобочитаемое Имя Тула — только для документации/графа, НЕ для вызова]
type: [linter | generator | preprocessor | aggregator | analyzer]
description: [Краткое описание работы инструмента]
department: [название отдела, например: discovery]
command:
  [
    базовая команда вызова,
    например: python -m departments.discovery.tools.linters.validate_pitch_deck.command,
  ]
inputs:
  - [глоб/путь к файлам, которые тул читает]
outputs:
  - [
      глоб/путь к файлам,
      которые тул пишет,
      либо 'stdout' если это линтер без,
    ]
contract: [опционально; путь к YAML-шаблону контракта в папке contracts/, например: departments/discovery/contracts/my_template.yaml]
contract_schema: [опционально; полный python-путь импорта Pydantic-схемы, например: departments.discovery.tools.linters.my_tool.schemas.MySchema]
cli_name: [опционально; CLI-глагол, если kebab-case имени директории неоднозначен
  или в промптах уже закреплён другой глагол, например: stress-test-economics]
cli_aliases: [опционально; список дополнительных имён-алиасов для той же команды]
```

**Контракты и Схемы (Contracts & Schemas):**
Если ваш инструмент генерирует или валидирует структурированные данные (YAML/JSON) с помощью Pydantic-схемы (`schema.py`), вы **обязаны** создать соответствующий YAML-шаблон в папке `contracts/` и указать поля `contract` и `contract_schema` в `meta.yaml`. 
Зачем это нужно? Pydantic-схема гарантирует техническую корректность в коде (Python), а YAML-шаблон с плейсхолдерами служит API-документацией для других LLM-агентов (поскольку агентам дорого и сложно читать исходники на Python). Вы должны поддерживать их синхронно вручную. В конвейере работает утилита `contract_diff.py`, которая отловит рассинхрон и упадёт, если вы обновите схему в коде, но забудете обновить YAML-контракт.

**Требование к `command.py`:** для авто-регистрации в глобальном пространстве алиасов модуль обязан экспортировать атрибут `command`, указывающий на Typer-функцию или экземпляр `typer.Typer()`, например `command = validate_pitch_deck_cmd`. Без `meta.yaml` и этого атрибута тул не получит алиас — генератор `scripts/build_aliases.py` сканирует `**/meta.yaml` и создаёт глобальные CLI-команды в `pyproject.toml`. Ручное редактирование файлов для регистрации нового тула не требуется. После добавления нового тула необходимо пересобрать алиасы командой `python3 scripts/build_aliases.py && pip install -e .`

## 2. Архитектурные Принципы (OOP / FP)

- **DRY (Don't Repeat Yourself) через Shared Libraries:**
  Запрещено дублировать функции парсинга Markdown, валидации YAML или извлечения регулярных выражений из файла в файл. Вся переиспользуемая логика (например, `split_zones`, `extract_xml_block`) обязана лежать в общей библиотеке (`departments/operations/tools/shared/` или `departments/<dept>/tools/shared/`).
- **Базовый YAML-автофикс — всегда включён, не опция:**
  `departments/operations/tools/shared/yaml_autofix.py` — кросс-департаментский модуль, который лечит повторяющиеся ошибки LLM-синтаксиса в YAML до попытки парсинга: экранирование апострофа бэкслешем внутри `'...'`, смешение `'`/`"` в одном скаляре, табы в отступах (`fix_tab_indentation`). `departments/discovery/tools/shared/file_utils.load_yaml` уже пропускает контент через `load_yaml_text`/`DEFAULT_FIXERS` — любой тул, читающий YAML через `shared.file_utils.load_yaml` (а не голый `yaml.safe_load`), получает этот автофикс бесплатно и молча, без отдельного флага/вызова. Если после фиксеров файл всё ещё не парсится — падает обычная ошибка парсинга, как и раньше.
  Новые точечные regex-фиксеры под другие повторяющиеся паттерны добавляются в тот же модуль (`DEFAULT_FIXERS`), но **только если правка однозначна и не требует угадывания намерения автора** — например, неэкранированное `: ` внутри нестрогового скаляра (`title: Note: важная деталь` → `mapping values are not allowed here`) сознательно НЕ автофиксится: regex не может надёжно понять, где реальная граница ключ/значение, а неверная догадка молча испортит данные вместо явного падения. Такие случаи остаются жёсткой ошибкой валидации, требующей от автора взять строку в кавычки.
  Другой пример того же паттерна для markdown, не YAML: `validate_markdown_links` (`rules/fixer.py`, `logic.py` с `fix=True` по умолчанию) уже всегда переписывает входной `.md`-файл перед валидацией — `meta.yaml` теперь честно декларирует файл и в `inputs`, и в `outputs`, а не только `stdout`.
  Инструменты, которым явно нужен отчёт "что было исправлено" по конкретному классу файлов (например `query_discovery`'s `fix-flow-yaml-quotes` для `flows/*.yaml`), остаются самостоятельными CLI-командами — это осознанно другой случай использования (explicit dry-run/report), а не дублирование самого фикс-движка.
- **Строгое Разделение Слоев:**
  - `schemas.py`: Только Pydantic-модели и валидация данных (схемы входа/выхода).
  - `logic.py`: Чистые функции (FP) или сервисные классы (OOP). Они принимают Pydantic-модели и возвращают Pydantic-модели (или кидают исключения). Никаких `print()`!
  - `command.py`: CLI-интерфейс (Typer). Отвечает исключительно за парсинг аргументов из Bash, вызов `logic.py` и `typer.echo()`/`sys.exit()`.
  - `__tests__/test_logic.py`: Unit-тесты для бизнес-логики.
- **Fail-Fast & Exit Codes:**
  Линтеры должны мгновенно падать с Exit Code 1 при первой же обнаруженной проблеме, выводя в STDERR понятное сообщение для LLM (что именно сломалось и где). При успехе — Exit Code 0 и короткий JSON в STDOUT.
- **Convention over Flags:**
  Если значение флага в 95% случаев одно и то же (например, всегда `workspace/discovery/strategy`), это не флаг, а константа — задавай `typer.Option` с дефолтом, указывающим на канонический путь воркспейса, вместо того чтобы требовать (`...`) его на каждый вызов. Обязательным (`...`) флаг/аргумент остаётся только тогда, когда его значение реально меняется между вызовами. Каждый лишний обязательный флаг — это ещё один шанс, что агент забудет его или напишет неверный путь.
- **Merge Trivially-Sequential Calls:**
  Если тул A (обычно линтер) всегда вызывается непосредственно перед тулом B на одном и том же файле, и B не имеет смысла запускать на невалидном входе — зашей вызов A как preflight-проверку внутрь `logic.py`/`command.py` тула B (fail-fast до основной работы), а не описывай два последовательных `<call_tool>` в промпте агента. Пример: `generate_pitch_deck` валидирует структуру `pitch_deck.yaml` внутри себя перед генерацией.

## 3. Явный вызов тулов из Агентов

Синтаксис тега `<call_tool>` (и парного `<read>`/`<write>`/`<for_each>` для файлового I/O и итераций) — единый для всех промптов и описан в `departments/operations/playbooks/skill-agent-crafting.md` (раздел "Теги Ввода-Вывода и Вызовов"). Здесь фиксируется только требование к самим тулам: любой вызов локального скрипта из `<workflow>` обязан быть обёрнут в `<call_tool name="...">`, где `name` — это CLI-глагол тула: kebab-case имя его директории, либо (если оно переопределено) значение `cli_name` из его `meta.yaml`. Человекочитаемое поле `name:` в `meta.yaml` для вызова не используется — оно только для графа/документации.

## 4. Вызов тулов из тулов (`calls_tools`)

Тул может использовать другой тул не только через CLI/`<call_tool>` (это делают только агенты), но и напрямую — импортируя его Python API (`from departments.discovery.tools.analyzers.query_discovery.logic.queries import ...`). Такой вызов невидим для статического анализатора (`departments/operations/tools/pipeline_analysis`), который парсит только markdown-разметку агентов и `meta.yaml` тулов — он не читает исходники на Python. Чтобы граф зависимостей и `WORKFLOW.md` оставались корректными, каждый такой вызов **обязан** быть продекларирован в `meta.yaml` вызывающего тула через `calls_tools:`.

**Формат:**

```yaml
calls_tools:
  - other-tool-name                # весь тул целиком — только для простых тулов
                                    # с плоскими inputs/outputs (например, линтер,
                                    # который вызывающий тул гоняет как preflight-проверку).
  - multi-command-tool::subcommand # тул с per-command inputs/outputs (см. ниже) —
                                    # ОБЯЗАТЕЛЬНО указывать конкретную подкоманду.
```

**Почему `::subcommand` обязателен для многокомандных тулов:** такие тулы (`type: analyzer` с ключом `commands:` в `meta.yaml`, например `query_discovery`) не имеют единого плоского `inputs:` — у каждой подкоманды свой набор читаемых файлов (см. `commands.<name>.inputs` в его `meta.yaml`). Если продекларировать `calls_tools: [query_discovery]` без подкоманды, анализатор свяжет вызывающий тул с самим базовым узлом тула, у которого нет собственных `inputs`/`outputs` — граф не получит ни одной реальной связи с файлами, либо (в худшем случае, если у тула когда-то появится плоский `inputs:`) вызывающий тул окажется зависимым от **всех** файлов, которые вообще когда-либо читает многокомандный тул, а не только от тех пяти-шести, что нужны именно вам. Указывайте только те подкоманды, которые тул реально вызывает — по одной строке на каждую использованную Python-функцию, с комментарием, какую функцию она отражает:

```yaml
calls_tools:
  - query_discovery::stories       # get_filtered_stories
  - query_discovery::data-model    # get_data_model_metrics
```

**Что это даёт в графе:** вызывающий тул получает `calls_tool`-ребро к узлу `<tool>::<subcommand>`, а сама подкоманда — прямые `reads`-рёбра от тех файлов, что перечислены в её `commands.<subcommand>.inputs`. На дашборде (`DASHBOARD.html`, вкладка Graph) читающие-только подкоманды схлопываются в прямые рёбра "файл → вызывающая сущность", подсвеченные зелёным (`PALETTE.readsEdge`) — точно так же, как для агента, вызвавшего тот же тул напрямую через `<call_tool>`. Разницы между "агент читает через тул" и "тул читает через другой тул" на графе нет — обе схлопываются в одинаковый прямой зелёный edge к конечному файлу.
